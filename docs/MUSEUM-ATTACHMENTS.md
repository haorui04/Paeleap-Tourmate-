# Artifact images and document descriptions

Little De Rabbit / 小德兔 now accepts one JPG, PNG, WebP, PDF, DOCX, TXT or Markdown file per question. The existing travel profile keeps its own attachment behavior. Other custom museum profiles remain disabled until explicitly supported; an upload cannot switch a conversation's persona.

Use **Attach**, choose a file, optionally describe what you want to identify, and send. A file-only message gets a museum-specific prompt. Users can also type an artifact description, such as “a hexagonal basin with seven hollow tubes — what artifact is it?”

Limits: documents and the final uploaded file are at most 2 MB; images may be at most 8 MB and 16 megapixels before browser resizing. Images are decoded, resized and stripped of metadata again on the server. PDF files are limited to twelve pages. Text extraction is limited to 12,000 characters. Encrypted, malformed, animated, oversized or unsupported files are rejected. The bounded document worker does not execute macros, links or document instructions.

## How identification works

### Direct Gemini image identity, then database lookup

Set `AI_IMAGE_IDENTIFICATION_PROVIDER=gemini_free`, `AI_IMAGE_IDENTIFICATION_MODEL=gemini-3.6-flash`, and a server-only `GEMINI_API_KEY` from Google AI Studio. Keep the key's Google project on its **Free** plan with billing disabled. The application cannot determine a project's billing plan from an API key. Both approved model IDs (`gemini-3.6-flash` and `gemini-3.5-flash-lite`) currently offer a Google Developer API Free tier, subject to quotas and account/region eligibility. Free-tier inputs may be used to improve Google's products; do not submit confidential files. Provider prices and availability may change.

Museum images bypass the older observation/feature-description and Commons-search flows below. The normalized JPEG goes directly to Google's fixed endpoint. Stage one receives no database records, candidate suggestions, filenames or chat history. It returns only bilingual candidate names and a bounded decision/confidence. This is learned model knowledge, not a queryable model database or independent verification.

Stage two runs locally on the server, comparing the bilingual names with artifact names in the conversation's published museum package. It requires a unique specific Chinese name supported by the English name, or multiple distinguishing English terms with a clear lead over other records. It compares names, never historical answer text. Generic names, conflicting bilingual names and tied matches cannot force a record selection. The model cannot return a record ID or write a catalogue description. For a match, the server returns **artifact name + published database description + reference links** (`museum_identity_match`). Otherwise it returns **candidate name + not matched in the current museum database** (`museum_identity_not_found`). Uncertain identification is reported separately and never asserted to be absent from the museum. Conservative name matching can miss an unrecorded synonym; a miss is not proof of absence.

No scene description, generated historical narrative or model-invented catalogue entry is shown on this route. Input checks run before inference; image instructions remain untrusted; bilingual names and the final server-rendered reply are checked again before output. Each identification normally makes **one** Gemini request using the dedicated key; database-name matching needs no further AI request. A transient HTTP 503 receives one bounded retry on the same free model. Authentication, quota, permission, malformed and timeout errors are never retried. The image route never uses the main chat/Gateway key, a paid-only model, Google Cloud Vision or external image search. A missing key, invalid model, exhausted quota or persistent provider outage stops the route without a paid fallback. Original image bytes are not saved in chat history. PDF/document handling and the separately configured main text-chat provider are unchanged. Older flows remain available only when both direct-image provider and model settings are absent.

`tests/gemini-image-identity.test.mjs` verifies name-first routing, both database outcomes, bilingual output, credential isolation, approved models, no paid/scene fallback, unsafe inputs, invalid identities, unknown record IDs, low confidence, and provider/quota failures. Live tests and fixtures are separate evidence.

References: [Gemini Free-tier pricing](https://ai.google.dev/gemini-api/docs/pricing), [Google's compatible API](https://ai.google.dev/gemini-api/docs/openai), [region eligibility](https://ai.google.dev/gemini-api/docs/available-regions).

### Earlier observation/reference route (used only without the direct-image setting)

1. Authenticate, enforce quota, verify conversation ownership and resolve its published persona version before decoding or analyzing a file.
2. The separately configured image-capable model reads visible features and exhibit-label text from images or PDFs. DeepSeek remains the main text model; binary images are never sent to a text-only DeepSeek endpoint. DOCX/TXT/Markdown use bounded text extraction.
3. Treat the attachment, OCR and visitor description as untrusted evidence. The existing prompt-injection, harmful-request and privacy checks still apply. Redact detected personal identifiers throughout extracted text before forwarding it for matching. Reject requests to identify real people or locate private homes.
4. DeepSeek first compares the evidence with artifact records from **this published museum persona only**. It returns record IDs and literal supporting quotes, not a free-form answer. A clear distinctive image can match without a label. Unknown IDs, invented quotes, duplicate fields, malformed envelopes, low-confidence visual claims and weak generic resemblance fail closed.
5. If that image match is uncertain, the vision model compares the visitor image with curated, licensed reference photographs bound to the same persona version. The starter photographic catalogue contains **one object: DS005, the seven-tube vessel**; the other records still use their textual references. It does not claim photographic coverage for every object. Add reviewed photographs and their attribution in `data/personas/deshou-images.js` and `public/artifacts/deshou/` to expand this stage. Updating a persona version requires reviewing its photographic mapping too.
6. If still uncertain, public Wikimedia Commons keyword image search supplies up to five candidate image-file names. No new search API key is required. Only bounded descriptive search terms are sent to Commons; the visitor image, filenames, documents, chat history and credentials are never sent there. This is narrower than whole-web reverse image search and can miss objects absent from Commons. Captions remain untrusted. Returned page/image URLs are never fetched by the backend. Google reverse search is an optional paid adapter, activated only when an administrator explicitly selects it.
7. DeepSeek cross-checks those naming hints against the original visible observations and this museum's records. A name/title alone is insufficient. Supporting quotes must come from original image observations, not web captions. Web material is untrusted data, cannot change the persona, is not automatically inserted into Supabase, and cannot supply new visitor-facing historical claims. The server checks that a candidate title also supports the selected record name.
8. The server renders the selected record's name, description and reference links with a visible **suggested match** notice. A web-assisted candidate gets a separate provenance label. It does not establish authenticity, ownership, an accession number, current display or exact location. No match produces “not matched in the available records,” **never “the museum does not have this artifact.”** Missing search configuration and temporary search failures are reported distinctly.

The selected catalogue is incomplete. Similar objects may exist at other museums; recognition is a candidate reference match, not an expert attribution. Human review remains appropriate for important identifications. Lexical grounding checks add a conservative boundary, not proof that the model understood every image correctly.

Raw files, image bytes, OCR and extracted document text are request-only. They are sent to the configured AI providers for processing, not used to train this application. Commons receives descriptive search terms only. Only explicitly selecting the optional Google adapter would send the normalized visitor image to Google Cloud Vision. The application stores the user's question, a bounded filename marker and the server-rendered reference reply/candidate links in the private conversation; it does not upload originals to Supabase Storage. Provider retention depends on each configured provider's terms. Avoid uploading personal or confidential documents. The curated photograph is by Siyuwj, CC BY-SA 4.0; source and license are recorded beside the asset and linked in photographic-match responses.

The referenced artifact can be discussed in follow-up using its published description in server-owned chat history. A new visual or document-specific detail requires reattaching the file. The UI distinguishes candidate matches, clarification and recognition-unavailable states; a provider failure never becomes a fabricated identification.

## Checks

Archaeological features have a separate visual-type path (`museum-features.js`): wells/wellheads, drains/channels, foundations and pools need not be portable catalogue objects. After the initial upload and OCR safety checks, the vision model inspects the actual image and returns a bounded feature type plus a literal observation quote. The server rejects unknown types, low confidence, invented evidence, duplicate/extra fields and unsafe content. It renders only fixed educational descriptions and a sourced Deshou context note, then checks the final text again. `museum_visual_description` explicitly distinguishes a possible feature type from an exact catalogue attribution. It never identifies the photographed well as a specific imperial well, dynasty or accession number from appearance alone. This path does not add or change Supabase persona records.

`AI_ARTIFACT_VISION_MODEL` optionally selects a stronger classifier for this feature path, independently of DeepSeek and the existing general upload model. The tested configuration uses `google/gemini-2.5-flash` through the existing gateway; AI usage charges still apply. Its response budget is 2,048 tokens to avoid truncating structured output. Supporting evidence is constrained to literal observation sentences by schema. If a wellhead cannot be distinguished from an embedded vessel, the answer names both possibilities rather than asserting a specific exhibit identity. A model's scope-redirect on otherwise safe museum evidence becomes clarification, not an accusation of malicious input. Unsafe visitor instructions and OCR remain blocked before classification.

`tests/museum-attachments.test.mjs` covers images, PDFs, labels and typed descriptions; privacy and later-page injection; malformed observation/matcher output; unknown/cross-museum IDs; invented evidence; generic-photo ambiguity; authentication, quota, ownership and persona binding; and private transcript persistence. The existing attachment suite verifies MIME/magic-byte agreement, image normalization, PDF rebuilding, DOCX protections and bounded parsing. Live provider and browser checks are recorded separately from these simulated service tests.

`tests/museum-image-search.test.mjs` additionally covers stage ordering, licensed photographic comparison, web-to-record cross-checks, rejected URL destinations/captions, secret isolation, response-size limits, outages, absent credentials, and excluding documents and unsafe OCR from search. These service fixtures verify routing and boundaries; they are not measurements of real-world image-recognition accuracy.

## Default search: no separate API fee

`MUSEUM_IMAGE_SEARCH_PROVIDER=commons` is the default. It needs no Google Cloud project, billing account or new search key. The existing vision and DeepSeek calls still consume your configured AI provider's usage; hosting limits still apply. Commons is a public service with usage rules, coverage limits and no application-specific availability guarantee. Calls are bounded, identify Tourmate in User-Agent, do not retry service failures and remain behind the existing account chat quota.

`MUSEUM_WEB_SEARCH_ENABLED=false` disables external image search. `MUSEUM_REFERENCE_IMAGES_ENABLED=false` disables only curated photograph comparison. `/api/status` reports the selected search provider and configuration boolean; these do not prove successful live search or recognition accuracy. Commons outages produce an honest clarification and never switch to a paid provider. A missing match never establishes that an object is absent from the museum.

The optional Google adapter requires explicitly setting `MUSEUM_IMAGE_SEARCH_PROVIDER=google` and privately supplying `GOOGLE_CLOUD_VISION_API_KEY` as a server-only Vercel Secret, then redeploying. It incurs separate Google charges. A Google key alone does not enable it when the selected provider is Commons.

The starter photographic catalogue is bound to persona version 1. Its reviewed visual features support tentative resemblance matching even when an initial observation is unsure about an object's exact name. Comparison output uses a strict schema and literal observed evidence; the final historical description always comes from the published museum record. This remains a probabilistic visual comparison, not authentication.
